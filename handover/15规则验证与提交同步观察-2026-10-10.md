## 4. 决策与理由

### 4.1 决策点：交接文档骨架是否保留「交付物与指纹」章

- **备选项**：甲，保留该章，新交接文档继续登记字节数、行数与 SHA-256；乙，取消该章，文件变更与版本回查交给 Git。
- **各自影响**：甲能让接手方在文档内直接读到生成当时的精确指纹，但每次改动都要重采、写死的值很快与磁盘不符，且登记值与实际文件的对应关系需要额外说明。乙少一章维护动作，指纹改由按需实测，代价是不看 Git 就拿不到历史值。
- **结论**：选乙。用户当轮直接删除了该章，骨架由九章变为八章，规则修改落在 [[01交接文档写作格式]] 第 2.3、3 章。
- **反悔方式**：在 [[01交接文档写作格式]] 第 3 章骨架中恢复该章与第 8 章对应自查项，并同步 `templates/handover-template.knap`、示例数据与 [[00模板说明]]。

### 4.2 决策点：是否引入 `.base` 视图承接索引与未决汇总

- **备选项**：甲，引入 `.base` 视图；乙，继续由 Markdown 表格承担。
- **各自影响**：甲可自动汇总，但要引入新文件类型与查看方式，与现有双链与表格口径并存会增加说明成本。乙维持现状，索引与汇总仍靠人工同步，代价是漏改风险由规则与自查承担。
- **结论**：选乙。这是用户明确决定，不是基于测试结果否决；该项按此闭环，未创建的视图不再补做。
- **反悔方式**：在 [[00handover总览]] 与 [[00模板说明]] 中恢复视图分工的表述，并新建 `.base` 文件。

### 4.3 决策点：是否把取指纹与格式自查做成脚本

- **备选项**：甲，做成可复用脚本；乙，继续按 [[01交接文档写作格式]] 第 8 章人工逐条执行。
- **各自影响**：甲能机械覆盖字节数、哈希、行数与部分 Markdown 格式，但九章骨架、元信息与未决表格的规则只适用交接文档，冻结历史保留旧章号与旧名称又不能按现行规范判错，脚本只能报告差异、无法判定合格；且试做版本曾把行内代码里的双链示例误判。乙保留人工判断，代价是每次交付前要花时间逐条过。
- **结论**：选乙。用户在试做脚本发现误判后决定不固化，脚本与配套测试文件已删除，工作区无残留。
- **反悔方式**：重新建立脚本与其 profile 划分，并在 [[10提交与文档同步规则]] 第 4.1 节恢复对应的自动化步骤。

### 4.4 决策点：是否派生其他交接文档模板

- **备选项**：甲，派生 `note/` 新笔记等模板；乙，只保留交接文档模板、示例数据与说明。
- **各自影响**：甲能统一更多文档的起点，但每个模板都要跟随规则改版同步，规则一改就要改多处。乙把模板面收窄到一处，规则变更的落点可控。
- **结论**：选乙。`templates/` 只保留交接文档模板、示例数据与说明，`note/` 骨架继续按 [[05Markdown规范]] 就地书写。

### 4.5 决策点：是否为本库的 Obsidian CLI 申请长期授权

- **备选项**：甲，申请一条长期授权规则；乙，需要时逐次授权。
- **各自影响**：甲减少重复确认，但把长期权限授予一个可读写库内文件的命令入口，与「只在必要时授权」的既有边界不符。乙每次都要人工确认，权限面最小。
- **结论**：选乙。该决策事项已在 [[13技能接入与模板目录-2026-10-08]] 第 3.1 节划线闭环，未创建长期授权规则，也未修改 DSH 配置。

### 4.6 决策点：「提交前先同步」的稳定性如何推进

- **备选项**：甲，增设自动化检查或脚本；乙，把已发现的失败模式补成规则内的预防项，并建立观察台账。
- **各自影响**：甲能机械拦截已编码的规则，但该事项的不确定性来自「漏了而没人发现」，脚本只能检查已知模式，还会与 4.3 的决定冲突。乙把已知模式固化为可执行条文，同时留下可判定的样本记录，代价是判定仍然依赖人的发现。
- **结论**：选乙。预防项落在 [[01交接文档写作格式]] 第 5、8 章与 [[10提交与文档同步规则]] 第 4.1 节第 2 步；台账落在该篇第 7.2 节表下，只记日期、提交范围、归类与依据。
- **反悔方式**：删除该篇第 7.2 节的台账与第 4.1 节第 2 步的补充，并撤回两处交接文档预防项。

### 4.7 决策点：台账收录哪些样本

- **备选项**：甲，收录全部历史提交中的补正；乙，只收规则定型后的工作单元，冻结文档遗留缺陷与纯事实写错不计入。
- **各自影响**：甲样本量大，但混入规则制定之前的返工与已冻结文档的旧口径残留，会把「规则未生效时期的记录」算成「现行规则的失败」。乙样本少，但每个样本都在现行规则下产生，判定才有意义。
- **结论**：选乙。用户明确指出：规则是逐步完善的，早期提交与已冻结交接文档的遗漏不应作为该事项的判据。判定口径是工作单元——一次「改完 → 同步 → 提交」为单元，同单元连笔算一个。
- **反悔方式**：在 [[10提交与文档同步规则]] 第 7.2 节台账表头改回全量收录口径，并重新分类现有样本。

### 4.8 决策点：模板渲染的验证方式

- **备选项**：甲，为验证写脚本或申请长期授权；乙，渲染到库内临时文档后用 Obsidian CLI 逐次授权核验。
- **各自影响**：甲省重复确认，但与 4.3、4.5 的决定冲突。乙每次需人工授权，但权限面最小，且核验的正是应用内的真实渲染结果。
- **结论**：选乙。核验完毕即删除临时文档与截图，验证路径见第 7 章。
- **反悔方式**：改用其他渲染核对方式，并在 [[01交接文档写作格式]] 第 7 章更新可复跑路径。

- 回滚会丢失什么：被回退提交之后写入的 [[当前状态]] 结果记录与规则预防项；模板侧八章改写若被撤销，需重新同步 `templates/handover-template.knap`、示例数据与 [[00模板说明]]，否则三者会与 [[01交接文档写作格式]] 第 3 章骨架不一致。
- 不回滚的替代方式：单点更正走 [[01交接文档写作格式]] 第 2.3 节允许的可改范围，事实与理由记入新的交接文档。

## 7. 复现方法

- 本阶段没有新增脚本文件；以下命令均为内联执行。

**模板渲染与结构核对**（在库根执行，环境：Windows PowerShell）：

```powershell
# 校验模板
knap validate templates/handover-template.knap

# 以示例数据渲染到系统临时目录
knap render templates/handover-template.knap --data templates/handover-data.example.json -o $env:TEMP\handover_render_check.md
```

- 预期输出：`knap validate` 打印 `Template is valid (static checks only; runtime values are not checked).`；渲染文件为八章骨架，检索「交付物与指纹」「SHA-256」为 0 命中，除正文示例外无 `{{` 与 `{%` 残留。

**应用内渲染核对**（`obsidian` 命令必须在沙箱外执行）：

```powershell
# 打开库内文档
obsidian open file=handover/<文件名>

# 切到阅读视图（eval 按表达式求值，return 需包在 IIFE 内）
obsidian eval code="(() => { const v = app.workspace.activeLeaf.view; v.setState({ ...v.getState(), mode: 'preview' }, { history: false }); return v.getMode(); })()"

# 取渲染后的标题（注意虚拟滚动，需逐段滚动收集后去重）
obsidian dev:dom selector=".markdown-preview-view h2" all
```

- 预期输出：模式返回 `preview`；标题数量与编号连续，与源文件结构一致。
- 长文档必须逐段滚动收集，单次查询只返回视口内的区块，直接统计会漏。

**敏感值扫描**：命令骨架与规则表见 [[10提交与文档同步规则]] 第 4.2、4.3 节，按第 4.1 节七步流程执行。
