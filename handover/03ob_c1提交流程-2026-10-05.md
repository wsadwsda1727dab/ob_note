## 4. 决策与理由

### 4.1 决策点：扫描与暂存的顺序

- 备选项：甲，先扫描再暂存；乙，先暂存再扫描。
- 影响：乙一旦命中，需要回退索引，容易留下半成品状态；甲的失败路径简单，索引与工作区都保持原样。
- 结论：选甲，并且做成 fail-closed——有命中就中止，`git add` 一次都不执行。
- 反悔方式：若将来把扫描并入提交钩子，顺序问题由钩子统一处理，本节作废。

### 4.2 决策点：判据是“见敏感值即拦”还是“只拦新增暴露”

- 备选项：甲，发现任何敏感值就中止；乙，只拦工作区新出现、`HEAD` 中不存在的值。
- 影响：甲会被历史既存内容永久卡死——本库就存在一个 SSH 克隆地址里的固定用户名，按甲的口径永远无法提交；乙需要逐值比对 `HEAD`，实现稍复杂。
- 结论：选乙，并保留甲的从严侧：任何**新值**无论硬禁级还是应当级一律中止。
- 反悔方式：把判据改回甲即可，代价是先清理历史里已存在的敏感值。

### 4.3 决策点：报告是否回显命中内容

- 备选项：甲，连命中片段一起打印，便于定位；乙，只报文件、规则与次数。
- 影响：甲的命中片段会进入终端回滚缓冲、日志与对话记录，使扫描记录本身变成新的泄漏点。
- 结论：选乙。需要定位时按文件与行号另行查看，不在报告里展开内容。
- 反悔方式：无必要。

### 4.4 决策点：提交是否包含推送

- 备选项：甲，提交后自动推送；乙，只提交，推送单独授权。
- 影响：甲会让未复核的内容直接进入远端历史，而远端历史不易撤回，且远端可能是公开仓库。
- 结论：选乙。推送是独立动作，一律需单独授权，本流程到 `git commit` 为止。
- 反悔方式：若将来远端改为完全可信的私有备份，可考虑自动推送。

### 4.5 决策点：是否把流程做成独立脚本

- 备选项：甲，做成可运行脚本；乙，写成命令骨架，按需内联。
- 影响：甲省手工，但绑 Windows PowerShell 5.1、执行策略、编码三个坑，还要额外维护规则清单文件；本库提交频率低，收益有限。
- 结论：选乙。2026-10-05 用户决定维持此结论：不把扫描固化为脚本，本项闭环。
- 反悔方式：把第 8 章的命令段存为脚本文件；注意脚本必须存为 UTF-8 带 BOM，否则中文会乱码并报语法错误。

### 4.6 决策点：提交与文档同步的先后

- 备选项：甲，先把该同步的改动做完再提交；乙，先提交，发现问题再补。
- 影响：乙省一次停顿，但提交动作本身会让刚提交的文档失真，只能追加补提交，而每次补提交都要重跑扫描、重算指纹；甲多一道自查，一次提交即形成自洽状态。
- 结论：用户定案选甲，已写进第 8.1 节第 1、2 步。
- 反悔方式：删掉第 8.1 节第 1、2 步即可，代价是恢复“提交后再补”的返工。

### 4.7 决策点：是否给提交信息定格式约定

- 备选项：甲，定一套格式约定（类型前缀、范围、长度等）；乙，不定格式，只沿用现有白话式写法。
- 影响：甲能统一历史措辞，但本库只有用户与 agent 两方、提交频率低，收益有限；一旦成规矩，就要写进第 8.1 节与自查清单，每次提交都要额外核对，而格式出错的代价仅是历史不好看，可回滚、无外部影响。乙沿用现状，配合已有的两条事实性约束（中文提交信息、UTF-8 无 BOM 消息文件 + `git commit -F`），可读性已够用。
- 结论：2026-10-05 用户定案选乙，不定格式约定，本项闭环。
- 反悔方式：补一节格式约定并写入第 8.1 节即可；已产生的历史无需改写。

### 4.8 决策点：是否补充 `.gitignore` 规则

- 背景：库内存在 `e3aa09d` 初始提交带入的 `.gitignore`（14 行），覆盖 OS 元数据、`.obsidian` 本地 UI 状态与缓存、`.trash/`，按本条事项的口径它不算「补充」。
- 备选项：甲，由 agent 拟定并提交一份新的忽略规则清单；乙，决定权保留给用户，agent 不列为待办、不主动推进。
- 影响：甲会引入一份未必符合用户习惯的清单，且当前库内无 `.bak`、无脚本产物等实际需要忽略的对象，收益低；乙保持现状，需要时用户自行补充。
- 结论：2026-10-05 用户定案选乙，本项闭环。
- 反悔方式：改为甲时，重开本条并明确要忽略的对象清单即可。

## 6. 回滚与恢复

- 命令在 Windows PowerShell 中执行；下列命令含破坏性选项，执行前先确认目标提交与当前分支。

```powershell
# 尚未推送：撤回最后一次提交，改动保留在工作区
git reset --soft HEAD~1

# 尚未推送：同时撤回暂存，改动回到工作区但不再 staged
git reset --mixed HEAD~1

# 已经推送：不要改写远端历史，改为追加一个反向提交
git revert <提交哈希>
```

- 何时应当回滚：提交信息写错、漏文件、或误把不该提交的内容带进了本地历史。
- 回滚会丢失什么：`--soft` 只动提交记录，不动内容；`--mixed` 会把暂存区清空；`git revert` 会新增一笔提交，原提交仍在历史里。
- 若敏感值已经入库：仅回滚提交不够，它仍留在历史中。需要改写历史，并且**必须同时轮换该凭据**——一旦推送过，就不能再假定它没有被读过。

## 8. 复现方法

### 8.1 标准流程

1. 先把该同步的改动做完再往下走：本次改动涉及的文档状态表述、指纹（字节数、行数与完整 SHA-256），以及 `handover/00总览-2026-10-05.md` 与库根 `README.md` 里的对应条目，全部纳入同一次提交。改完 `handover/` 文档要回头检查索引，索引更新后要回头检查引用它的文档。
2. 检查待提交文档里有没有会随提交动作变化的事实：未提交清单、提交笔数、提交序号。有则改成指向 `git log`、`git status` 的表述，不要把当下状态写死进文档。
3. 取得待提交路径清单，含未跟踪目录内的文件。
4. 逐文件比对工作区与 `HEAD` 的命中值，只对新增值拦截；有新增即中止，不暂存。
5. 打印报告：文件、规则、命中次数，不回显内容。
6. 全部通过后暂存，复核暂存统计，再提交。
7. 推送不在本流程内，需单独授权。

### 8.2 命令骨架

```powershell
$repo = 'D:\User\Documents\Obsidian\ob_c1'
$sd = @('-c', "safe.directory=$repo", '-c', 'core.quotepath=false', '-C', $repo)

# 1. 待提交路径（含未跟踪目录内的文件）
$por = @(git @sd status --porcelain=v1 --untracked-files=all)

# 2. 扫描：工作区命中值与 HEAD 命中值逐值比对，只有新值才中止
#    重命名过的文件要连旧路径一起取 HEAD 内容，否则会把改名当成新增暴露

# 3. 通过后暂存与提交
git @sd add -A
git @sd diff --cached --stat
git @sd commit -m '<提交信息>'
```

### 8.3 扫描规则

- 硬禁级：GitHub Token、GitHub PAT、`sk-` 前缀的长密钥、AWS Access Key、私钥块、`password`／`secret`／`api_key` 等键值型凭据、内网 IP、本机主机名。
- 应当级：真实用户名、邮箱地址。
- 已移除「第三方中继域名」：中继域名属于会随订阅与服务商变化的不稳定项，写进扫描规则即成为需要持续维护的易变事实（违背 [[05Command]] 第 13 章的口径）；且域名出现在文档中本身不构成敏感值，补 pattern 只会命中官方文档链接一类正常引用，并加重误报。该风险改由 `%USERPROFILE%\.dsh\AGENTS.md` 的外发条款以行为约束覆盖（外发前须列出原文片段与目的地并取得同意）。2026-10-05 用户定案。
- 报告只输出文件、规则与命中次数；**不得**回显命中内容。
- 已知误报：邮箱规则会命中 SSH 克隆地址里的固定用户名（形如 `git@` 加域名）。判定要按字面量确认，不能只看正则是否命中，也可把该常量直接列入白名单。
- 自撞风险：若文档里为了说明规则而写出“规则名本身”，宽松写法可能自撞；规则里的长度阈值（例如密钥至少 20 个字符）能避免这一类自撞。

## 9. 环境速查

- **笔记库 Git**：`ob_c1` 是 Git 仓库，`main` 跟踪 GitHub 上的 `origin/main`；提交与推送是两个独立动作，推送一律需单独授权。已核实。
- **远端比较的口径**：判断领先或落后用的是本地缓存的远端引用；未执行 `git fetch` 时，远端最新提交不可见。已核实。
- **表格会被编辑器重排**：文档经外部编辑器格式化后，表格会补齐空格并把分隔行的破折号拉长，从而产生未提交改动（实测某次多出 68 字节，忽略空白后仅剩分隔行长度变化）。提交前先确认 diff 是否只属这类变化。已核实（触发者推测为 Obsidian 的表格格式化）。
- **库的完整性标签**：库根与 `note`、`handover` 均带 Low 标签，新建对象自动继承。已核实。
- **沙箱内无法完成需认证的推送**：2026-10-05 实测（git 2.55.0.windows.5，远端 HTTPS、`credential.helper=manager`、`http.sslBackend=schannel`）——默认 schannel 后端 TLS 直接失败（`SEC_E_NO_CREDENTIALS`）；改用 `-c http.sslBackend=openssl` 后 TLS 通过，但任何 credential helper 被调用时都会冒出 msys 报错 `sh.exe: *** fatal error - couldn't create signal pipe, Win32 error 5`（沙箱禁命名管道），取不到凭据并报 `fatal: unable to get password from user`；把 helper 清空后该报错消失，证明由 helper 调用引起。**结论：推送一律由用户在沙箱外执行**（Obsidian Git 插件或本机终端），沙箱内 `git commit` 本身正常。已核实（详见 [[02DSH全局指令安全边界-2026-10-05]] 第 9 章）。
- **若要把流程存为脚本**：Windows PowerShell 5.1 要求非 ASCII 脚本存为 UTF-8 带 BOM，且直接调用 `.ps1` 可能被执行策略拒绝，需临时放开。详见 [[02DSH全局指令安全边界-2026-10-05]] 第 9 章。已核实。
