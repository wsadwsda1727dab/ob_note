## 1. 适用范围与优先级

### 1.1 适用范围

- 本规范适用于 `handover/` 下的全部交接记录类文档，即记录某一工作阶段状态的文档。
- 本目录另有三类不属交接记录：总览 `00`、写作规范 `01` 与 `当前状态`（在用状态文档）；其定位与维护规则见 1.2 节。
- 交接文档的用途是把某一工作阶段在特定交接时点的状态移交给未来的自己或未来的 AI，不是记录对话过程。
- 交接文档形成并完成交接后，作为该阶段的**历史状态快照**保存；后续工作状态、未决事项与变更不在原交接文档中持续维护。
- 现行口径以最新的交接文档与 1.2 节列出的三份文档为准；已冻结的历史交接文档只用于回查当时的决策、验证与路径，其章号、文件路径与规则表述可能已被后续文档取代，出现不一致时一律以后者为准。

### 1.2 三份非交接记录类文档

- `00handover总览`、`01交接文档写作格式` 与 `当前状态` 不属交接记录，不套用第 3 章的章节骨架，也不写元信息「承接自」，但都遵守 [[05Markdown规范]] 的格式规则。
- 三份的职责不同：`00handover总览` 是历史交接文档的索引与归档导航；`01交接文档写作格式` 是本目录的写作规范正本；`当前状态` 是**当前工作状态的唯一正本**，骨架与维护规则见第 9 章。
- `当前状态` 与历史快照的分工：前者回答「现在在哪里、下一步做什么」，持续维护、允许更新；后者回答「当时是什么状态、为什么这样决定」，形成后冻结。两者不得互相替代——把历史快照当当前状态读会拿到过期口径，把当前状态写成历史快照会失去持续维护的意义。
- `当前状态` 是**未决事项的唯一汇总处**：会话中新产生的待定项直接记入本篇第 4 段并写明状态，不再要求先写入当次交接文档再汇总到 `00handover总览` 第 5 章，也不要求「来源文档划线 + 总览删行」的双写动作。历史交接文档中的未决事项按形成时的原样保留，作为当时记录，不追溯改写。
- 交接文档的正文以实际工作与「承接自」的上一篇交接文档为来源；`当前状态` 可为交接文档提供「当前进行到哪一步」的背景，但不作为其决策、验证与环境条目的依据。
- 三份都不冻结，各自的更新时机：
  - `00handover总览`：目录内新增、改名或删除交接记录时更新。
  - `01交接文档写作格式`：本目录规则变更时更新。
  - `当前状态`：按第 9.2 节的事件驱动触发条件更新，不限于阶段开始或结束。
- 维护责任：规则或目录结构发生变化时，由当次执行人（用户或 AI）在同一批改动里同步 `01交接文档写作格式`、`00handover总览` 与 `当前状态`，不得只改一处而让其余文档保留相互冲突的要求。
- 本阶段暂无此类内容时写一行「暂无」。指向别处的表述要能直接点开，不写「见前述」「见上文」这类无法定位的说法。

### 1.3 与 [[05Markdown规范]] 的关系

- 交接文档**必须**同时遵守 [[05Markdown规范]] 的全部格式规则：标题层级与编号、章节末尾分隔线、空行、列表缩进、中英文之间的空格、标点、表格、代码块语言标注、术语写法。
- 本规范只补充交接文档特有的要求，不重复定义格式规则。
- 两者冲突时，以本规范为准。

### 1.4 冲突优先级

1. 用户当次的明确要求
2. 本规范
3. [[05Markdown规范]]

- 无法满足本规范的某条要求时，**必须**在回复中说明是哪一条、为什么不满足，**不得**静默忽略。

### 1.5 为什么不抄对话

- 对话里有大量过程噪声（试错、失败尝试、重复操作），逐字存档会把噪声固化成事实。
- 结论分散在多轮里，接手方需要的是可直接执行的当前状态，而不是推演过程。
- 对话原文已存在于 DSH 的会话记录中，再抄一份是重复存储，且必然过时。
- 交接文档只写四样东西：当前状态、决策与理由、未决事项、复现方法。

## 2. 存放位置与命名

### 2.1 存放位置

- 交接文档统一放在库根 `handover/` 下（本库的远端仓库名是 `ob_note`，本地工作目录名可能为 `ob_c1` 等，见 `AGENTS.md` 第 1.1 节）。
- 交接文档是阶段性产物，与 `note/` 下的长期知识分开存放，避免污染笔记编号序列；目录分工见 [[05Markdown规范]] 第 8.2 节与 [[00note总览]]。
- 若以后要求把交接文档迁回 `note/`，**必须**同步迁移全部文件，并更新双链与 [[00handover总览]] 索引。

### 2.2 文件命名

- 文件格式：`NN主题-YYYY-MM-DD.md`，`NN` 为两位顺序号，00总览、01格式、当前状态三份文档不受命名格式约束。
- 交接记录类文档从 `02` 起编号，新增时取本目录当前最大序号加一；`00`、`01` 与 `当前状态` 不占用编号。
- 主题用中文连写，不加下划线；英文缩写保留术语表写法。
- 本目录**不使用** `note/` 的 `NN名称.md` 编号形式：顺序号之后必须接主题与日期，由顺序号承担排序、日期承担版本标识；总览文档和规则文档除外（例如 00、01）。
- 示例：`02DSH全局指令安全边界-2026-10-05.md`。
- 改名或调整顺序号后，**必须**同步更新 [[00handover总览]] 的索引，以及引用它的双链。
- 文件名中不得出现 `\ / : * ? " < > |`，也不得有首尾空格。

### 2.3 阶段性交接文档的创建与冻结

- 交接文档不再要求**每个工作阶段都必须新建**：日常工作状态由 [[当前状态]] 持续维护，只有满足下面任一触发条件时，才为本阶段建立一份交接文档作为历史归档。
- **创建触发条件**，满足任一即建：
  - 用户明确要求保存、归档或交接。
  - 一个可独立验收的阶段性成果已经完成，且关键结论、证据、限制或复现步骤无法仅靠 [[当前状态]] 与已有文档清楚恢复。
  - 一项影响后续工作的关键决策已经确定，且未来可能需要追溯其依据、被否决的方案或验证证据。
  - 一次复杂的故障排查已得出可复现的结论，且需要保留完整的排查链条。
- **默认不建**的情形：
  - 仅开启或结束一次会话。
  - 只完成普通文件编辑、常规提交、格式修正或索引更新。
  - [[当前状态]] 与 `note/` 已完整记录结果，且 Git 历史足以恢复该变化。
  - 事项仍处在探索阶段，尚无值得冻结的独立结论。
  - **判不出来时默认不建**，但应更新 [[当前状态]]，并把已验证、有复用价值的结论写入 `note/`；不确定某项是否有历史价值时，先保留现有信息，不擅自删除。
- 每份交接文档对应一个明确的工作阶段或交接时点，形成后原则上作为**阶段性快照冻结**，不因后续工作进展而持续改写。
- 同一主题后续进入新的工作阶段时，应新建交接文档记录新的状态、决策、验证结果与未决事项，不覆盖或改写上一阶段的历史记录。
- 新增交接记录类文档时，**必须**在元信息「承接自」写上一阶段交接文档的双链，无上一阶段写「无」。
- 仅当发现原文档存在**事实错误、格式错误或结构性遗漏**，且修正不会改变该阶段的历史状态时，才允许对已形成的交接文档进行更正；更正只改错误本身，其事实与理由记入 `当前状态` 文档或新的阶段性交接文档。如更正会改变历史判断，应新建后续交接文档说明变化原因。
- 阶段性交接文档冻结后，除下一条列出的两处可改位置外，后续新增的变更、已解决的未决事项和新的工作状态不得回写原文档；需要记录时，应写入当前正在使用的工作状态文档或新的阶段性交接文档。
- 冻结后可改的位置只有两处：元信息「最近更新」与「未决事项与下一步」章（新模板为第 3 章，2026-10-08 前的旧模板为第 7 章）；事实错误、格式错误与结构性遗漏的更正属于上一条的例外。其余章节一律不回写。
- 2026-10-10 取消「交付物与指纹」章的调整适用于后续新交接文档；已冻结的历史交接文档保留原骨架、原指纹与原章号，不批量回改。历史引用按对应版本的章节含义阅读，不直接套用新骨架章号。

## 3. 文档骨架

```markdown

> 文档名称：<交接主题>
> 交接范围：<覆盖的文件、系统与时间范围>
> 交接状态：<从第 4.2 节的状态表取一个值>
> 接手方需要先知道：<一句话，最重要的那一条>
> 承接自：<上一阶段交接文档的双链；无则写「无」>
> 最近更新：YYYY-MM-DD
> 关联文档：[[...]]

**目录**

- [[#1. 状态摘要]]
- [[#2. 当前工作状态]]
- [[#3. 未决事项与下一步]]
- [[#4. 决策与理由]]
- [[#5. 已验证与未验证]]

### 3.2 可自行推进

## 4. 决策与理由

## 6. 回滚与恢复

```

- 交接记录类文档的元信息**必须**含「承接自」：承接上一阶段时写上一份交接文档的双链，本篇为同主题首篇时写「无」。
- 新交接文档采用上述八章骨架，不另设「交付物与指纹」章，不要求登记文件字节数、行数或 SHA-256；文件变更与版本回查由 Git 承担。
- 骨架中的章节不得删除；某章确无内容时写「无」并说明原因。
- 总览 `00`、写作规范 `01` 与 `当前状态` 不属交接记录，按各自职责维护，不套用本节骨架，三者列为跨篇引用。
- 交接文档冻结后，不再追加「变更记录」章节；后续变化应进入新的状态记录或新的阶段性交接文档。

## 4. 各章节内容要求

### 4.1 状态摘要

- 三行以内说明：现在是什么状态、接手方是否需要立刻行动、最重要的一条结论。
- **必须**做到只看这一节就能判断要不要继续往下读。
- 此处的「现在」指**本交接文档所对应的交接时点**，不是未来阅读该文档时的实时状态。

### 4.2 当前工作状态

- 交接状态从下表选取一个值。

| 状态 | 含义 |
|---|---|
| `进行中` | 当前工作还没有完成，接手后需要继续推进 |
| `已完成` | 当前阶段预定目标已经完成，暂时不需要继续推进 |
| `部分完成` | 阶段目标未全部完成，已有明确遗留需接手方推进 |
| `已暂停` | 工作暂时停止，后续仍可能恢复 |
| `已终止` | 该方向已经决定不再继续 |

### 4.3 未决事项与下一步

- 本节记录**本阶段交接时点尚未闭环的事项**，以及接手下一阶段时需要关注的入口。
- 分「等用户决定」与「可自行推进」两类，分别写作 3.1、3.2 两个小节，避免接手方把该问的当成该做的。
- 「等用户决定」小节写成四列表格，表头固定为 事项、前置条件、优先级、决定方，每项写全四件事；闭环时只改「事项」一列，写法见 [[05Markdown规范]] 第 14 章。无未决项时表内写一行「无」。
- 「可自行推进」小节逐条列出，不用表格。
- 未决事项后续闭环后，只按 2.3 节的可改范围处理「未决事项与下一步」章，闭环标注写法见 [[05Markdown规范]] 第 14 章；闭环结论本身记入 `当前状态` 文档或新的阶段性交接文档。
- 若需要长期保留该事项的解决结论，应将稳定结论整理进入 `note/`。

### 4.4 决策与理由

- 每条决策**必须**写全四项：决策点、备选项、各自影响、结论。
- **必须**记录被否决的选项与否决理由，否则接手方会重复讨论同一件事。
- 结论若可反悔，写明反悔需要改哪里。
- 若后续阶段推翻本阶段决策，不回写本节（可改范围见 2.3 节）；在新的阶段性交接文档中记录新的决策及变化原因。

### 4.5 已验证与未验证

- **必须**分成两栏，不得混写；这是交接文档里最影响接手判断的一节。
- 已验证：写明验证方式与证据，例如命令、输出、哈希、实测结论。
- 未验证：写明为什么没验证、是否影响使用。
- 推测**必须**显式标注为推测，不得写成结论。
- 「未验证」记录的是**本阶段交接时点**的验证状态；后续完成验证时，不回写本阶段快照（可改范围见 2.3 节），应在新的工作状态或后续交接文档中记录。

### 4.6 回滚与恢复

- 给出备份路径（脱敏）与可直接执行的恢复命令。
- 命令**必须**标注执行环境，见 [[05Markdown规范]] 第 6.2 节。
- 说明什么情况下应当回滚，以及回滚会丢失什么。
- 回滚信息针对本阶段交接时点的状态；后续状态发生变化时，不要求回写历史交接文档（可改范围见 2.3 节）。

### 4.7 复现方法

- 给出可复跑的命令或脚本骨架，以及它们的存放位置。
- 脚本与文档分离：脚本放独立文件，文档只写调用方式与预期输出。
- 复现所需的密钥、账号、环境变量一律用占位符，不写真实值。
- 复现方法针对本阶段交接时点的状态；若后续流程发生变化，应在新的交接文档中记录新方法。

### 4.8 环境速查

- 记录接手方需要知道的环境事实：沙箱策略、权限能力、网络出口、工具版本、路径约定。
- 每条**必须**标注「已验证」或「推测」。
- 环境发生后续变化时，不回写已经冻结的历史交接文档（可改范围见 2.3 节）。

## 5. 格式细则

- 全部格式规则继承 [[05Markdown规范]]，此处不重复。
- 交接文档在其之上收紧或补充如下：

  - 元信息**必须**含「交接状态」「接手方需要先知道」「承接自」与「最近更新」四个键。
  - 元信息各键**不得**写入入库或提交状态：不写「已提交」「尚未提交」「已入库」这类断言，改为指向 `git log`、`git status`，或写与提交无关的指引（如用法所在文档）。理由见 [[05Markdown规范]] 第 13 章；元信息是可改位置，不随提交失真这条更要注意。历史已成文文档中的同类断言按 2.3 节的例外更正。
  - 章节数达到八章时**必须**加目录（按本篇实际章节数计）；[[05Markdown规范]] 第 8.5 节为「应当」，交接文档收紧为「必须」。
  - 差异、命令、脚本一律用带语言标注的代码块，不得用无标注块代替。
  - 表格单元格内不换行；内容过长改用列表或拆分表格。
  - 文档以最后一章的 `---` 加换行结束，见 [[05Markdown规范]] 第 3 章。
  - 哈希、路径、命令用行内代码或代码块，不要写成普通正文。
  - 文档中**不得**写入会随提交动作变化的事实：未提交清单、提交笔数、提交序号；这类信息写成指向 `git log`、`git status` 的表述，避免提交动作本身让文档失真。该要求已提升为全库规则，见 [[05Markdown规范]] 第 13 章，此处只作提示。
  - 阶段性交接文档冻结后，不得为了维护当前状态、闭环未决事项或追加后续变更而回写历史内容；可改范围见 2.3 节。

## 6. 敏感信息处理

- 继承 [[05Markdown规范]] 第 9 章，并对交接文档收紧如下。

### 6.1 绝对禁止出现

- 真实 token、密码、私钥、cookie、会话标识。
- 内网主机名与真实用户名。

### 6.2 路径写法

- 统一写成占位形式：`%USERPROFILE%`、`C:\Users\<用户名>`、`<主机名>`。
- 确需记录绝对路径时只写盘符与目录层级，不写用户名。

### 6.3 写入前必查

- 命令输出、日志片段写入前**必须**先脱敏，不能整段照抄。
- 交接文档常出现「读过哪些文件」，写入前**必须**逐条检查：该路径、该文件名本身是否泄露隐私或敏感主题。
- 若交接内容涉及凭据的存在，只写其位置与用途，**不得**写内容，也**不得**把凭据读取到上下文后转述。

### 6.4 提交前扫描

- 库内提交前**必须**先扫描、后暂存；有命中即中止，不执行 `git add`。
- 判据是“只拦截新增暴露”：命中的值若已存在于 `HEAD`（含重命名前的旧路径）则为既存，放行并记录；出现任何新值一律中止。
- 硬禁级规则：token、私钥块、键值型凭据、内网 IP、本机主机名；应当级规则：真实用户名、邮箱地址。
- 报告只输出文件、规则与命中次数，**不得**回显命中内容。
- 已知误报：邮箱规则会命中 SSH 克隆地址里的固定用户名，判据按字面量确认，常量可列入白名单。
- 只提交到本地；推送是独立动作，需单独授权。
- 完整流程见 [[10提交与文档同步规则]] 第 4 章。

## 7. 可复跑资产

- 与交接内容配套的脚本、校验片段**应当**作为独立文件放在 `handover/` 下，并在文档中用双链引用。
- 跨阶段复用的模板与示例数据不放本目录，统一放在 `templates/`，用法见 [[00模板说明]]；本目录只放与某一阶段交接内容一一对应的资产。
- 图片、PDF、压缩包等附件按 [[05Markdown规范]] 第 8.6 节放在 `note/attachments/`，不要放在 `handover/`。
- 脚本**必须**可独立运行，不依赖文档里的手工步骤；前置条件写在脚本头部注释中。
- 脚本文件名同样带日期，格式：`主题-YYYY-MM-DD.ps1`。
- PowerShell 脚本**必须**存为 UTF-8 **带 BOM**：Windows PowerShell 5.1 读取无 BOM 的非 ASCII 脚本会按 ANSI 解码，导致中文注释乱码并报语法错误。这是对 [[05Markdown规范]] 第 8.3 节「不带 BOM」的有意例外，该节约束的是 Markdown 文档。
- 脚本的可运行性**应当**在交付前实测一次，不能只靠语法解析通过；本机默认执行策略会拦截未签名脚本，实测时需临时放开。

## 9. `当前状态` 的骨架与维护

> 本章定义 `当前状态` 这一份**在用工作状态文档**的骨架与维护规则。第 3 章定义的是历史交接文档的骨架，两套骨架服务不同对象，互不替代。

### 9.1 骨架

`当前状态` 采用六段式，顺序固定、段落不得删除；某段确无内容时写「无」并说明原因。

| 段  | 标题         | 记什么                                |
| --- | ---------- | ---------------------------------- |
| 1   | 当前任务与范围    | 现在在做什么、边界到哪里、承接自哪一篇                |
| 2   | 当前进度       | 已完成、进行中、未开始，各一行说明                  |
| 3   | 已确定的关键结论   | 后续工作依赖的结论，每条写明结论与它成立的条件或限制         |
| 4   | 未解决问题      | 尚未闭环的事项，含状态、前置条件、决定方与去哪儿跟踪         |
| 5   | 下一步行动      | 接手方接着要做什么，可执行、可核对                  |
| 6   | 相关入口与环境    | 继续工作需要打开的文件、命令与运行环境要点              |

元信息至少含「当前项目」「当前阶段」「最近更新」与「关联文档」四键；「状态」键若保留，取值改为简短枚举（如「进行中」「已暂停」），不再写叙述性长句，原叙述内容按其性质移入第 1 段与第 4 段。

### 9.2 维护规则

- **更新触发条件（事件驱动）**，满足任一即更新：
  - 当前任务、目标或范围发生变化。
  - 出现新结论，改变了原有方案。
  - 实验、排查或代码修改取得影响后续工作的结果。
  - 未决事项解决、新增或改变优先级。
  - 下一步行动发生变化。
  - 一次有实质进展的工作会话即将结束。
- **自包含程度**：第 1、3、4、5 段**必须**直接写出内容，不能只留指针——接手方只读本篇就应知道「停在哪里、为什么、下一步做什么、有什么限制」。完整实验记录、原始日志、验证数据与长期知识正文可以只给指针。
- **不能只留指针的判据**：若没有摘要就无法理解结论为何成立、有何限制、下一步为何这样安排，就**必须**保留原因与限制；不确定时保留，不因「已在别处写过」自动删除。
- **单正本**：同一事项只在本篇留一份当前口径，不在 `00handover总览` 或历史交接文档里重复维护。
- **清理策略**：完成不等于可删除；删除前**必须**有替代依据（已完成 + 结果有可靠的持久记录 + 不再是下一步决策的必要上下文，三条同时满足）；移出的内容**必须**能通过明确路径或链接找回。
- **时效声明（可选）**：可写明「最近核验时间」与「核验范围」一句，但不写成长篇报告；核验时间过旧不代表结论失效。

### 9.3 恢复时的核对

接手方（人或 AI）按本篇恢复工作时，逐项核对，不一致以**最新证据**为准并修正本篇：

| 核对对象            | 核对方式                                            |
| --------------- | ----------------------------------------------- |
| 当前任务、目标与下一步     | 对照实际待办与相关文件                                     |
| 文件是否存在、路径是否有效   | 检查文件与链接；失效的修指针，保留有价值的旧记录                        |
| Git 分支、提交与工作区状态 | 读实时状态，以 `git status`、`git log` 为准，不信文档里的旧动态值    |
| 关键结论及其依据        | 检查所引用的代码、数据与实验结果；不一致标为「待复核」，不把旧结论直接当现状          |
| 未决事项是否已解决       | 查实际证据而非措辞，有证据才关闭                                |
