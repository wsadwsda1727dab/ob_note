## 4. 决策与理由

### 4.1 交接文档是否继续作为每个工作阶段的默认产物

- 决策点：原规则要求「一个阶段一份文档」，导致规则维护本身也按阶段产出快照，快照数量随会话次数增长。
- 备选项：
  - 甲，保持每阶段必建。影响：历史完整，但维护成本与实际价值脱节，多数快照只记「我改了一条规则」。
  - 乙，彻底取消交接文档。影响：体积最小，但历史一旦被覆盖，回滚依据与决策理由永久丢失。
  - 丙，缩小为有条件的历史归档产物（四条触发条件 + 「判不出来时默认不建」）。
- 结论：选丙。用户 2026-10-16 拍板「冻结机制缩小，不取消」。
- **被否决的选项与否决理由**：否决乙——彻底取消会让历史失去稳定性，取消后旧口径被覆盖、回滚依据永久丢失；代价是不可逆的，而甲的代价只是体积。否决甲——默认产出把「该不该留档」的判断成本转嫁给每次工作，收益与成本不匹配。
- 反悔方式：把 [[01交接文档写作格式]] 第 2.3 节的四条触发条件与默认不建条款删除，恢复「每阶段一份」即可回到甲；回到乙需先确认历史快照确实不再被引用。

### 4.2 六段式骨架放在 `handover/01交接文档写作格式.md` 的哪一章

- 决策点：`当前状态` 需要一套与历史快照不同的骨架（六段式），而 `01` 现有第 3 章规定的是历史快照的八章骨架。
- 备选项：
  - 甲，改写第 3 章，让两套骨架合用一章。
  - 乙，重排章号，把历史快照骨架后移，腾出位置。
  - 丙，新增独立第 9 章「当前状态的骨架与维护」，第 3 章不动。
- 结论：选丙。
- **被否决的选项与否决理由**：否决甲与乙——第 3 章被全库多处以「第 3 章的八章骨架」指名引用，且 `templates/` 下三件资产（`00模板说明.md`、`handover-template.knap`、`handover-data.example.json`）硬绑在这一表述上；动第 3 章或重排章号会连带改 `templates/` 与大量章节引用，而两套骨架分别服务于历史快照与在用状态，本不构成正本冲突。
- 反悔方式：把第 9 章内容并入第 3 章并同步 `templates/` 三件资产与全库章节引用；这是一次跨目录改动，需按改名同级的谨慎程度处理。

### 4.3 未决事项的唯一汇总处

## 6. 回滚与恢复

- 备份路径：无独立备份。改造前的状态由 Git 承担，回滚依据是提交历史。
- 可直接执行的恢复命令（执行环境：Windows，Git Bash；两个占位符按 `git log` 的提交说明定位：`<改造前提交>` 为本次改造开始前的那个提交，`<改造后提交>` 为本次改造的最后一个提交；不在此写死哈希或序号）：

```bash
cd /d/User/Documents/Obsidian/ob_c1
git revert --no-commit <改造前提交>..<改造后提交>
git status   # 核对工作区，确认无误后再提交
```

- 什么情况下应当回滚：改造后的规则在实际使用中被证明不可行（例如「判不出来时默认不建」导致该留档的阶段普遍不留档），或用户决定恢复「每阶段一份」的旧口径。
- 回滚会丢失什么：`git revert` 会新增一笔反向提交，原提交仍在历史中，因此**不会**丢失改造过程本身；会丢失的是新生效的口径，以及 `.gitignore` 对三个 `kb-*` Skill 的跟踪（三个 `SKILL.md` 文件本身仍在磁盘上，可再次纳入）。第 4 章记录的被否决理由不受影响，它在本篇里。
