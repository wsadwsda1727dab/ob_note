## 2. 规则一：提交前先同步

### 2.1 规则内容

- 动手 `git commit` 之前，先把本次改动引发的所有关联变动做完，纳入同一次提交。
- 顺序是「改完 → 同步 → 提交」，不是「提交 → 发现过时 → 再补一笔」。
- 改完 `handover/` 文档要回头检查索引；索引更新后要回头检查引用它的文档。
- 落地步骤与命令骨架见第 4 章。

### 2.2 需要同步什么

- **文档状态表述**：受影响文档里对当前状态的描述。
- **指纹**：仅当本次改动涉及仍登记指纹的历史交接文档时同步；自 2026-10-10 起新建的交接文档不登记字节数、行数与 SHA-256，见 [[01交接文档写作格式]] 第 2.3、3 章。
- **索引条目**：`[[00handover总览]]` 与库根 `README.md` 里的对应行。

- 判据只有一句：这次改动会不会让别的文件里的某句话变成错的？会，就在提交前改掉。

### 2.3 理由与代价

- **代价对比**：先同步多一道自查；先提交省一次停顿，但提交动作本身会让刚提交的文档失真，只能追加补提交，而每次补提交都要重跑扫描、重算指纹。
- **结论**：选先同步，一次提交即形成自洽状态。
- **被否决的选项**：先提交、发现问题再补。
- **反悔方式**：删掉本篇第 2 章与第 4.1 节第 1 步即可；[[03ob_c1提交流程-2026-10-05]] 第 8.1 节是冻结的历史记录，不回改。
- **已知局限**：这条规则有效但不自动成立——改为该规则之后仍出现过返工。

## 3. 规则二：不写会随提交动作变化的事实(正文见[[05Markdown规范]]第13章)

### 3.1 规则内容

- 文档里**不得**写入会随提交动作变化的事实，改为指向 `git log`、`git status` 的表述。
- 原因是自指问题：当文档描述的状态里包含「这份文档自己有没有被提交」这件事时，提交动作一发生，描述立刻失真。

### 3.2 哪类事实属于禁止项

| 类别 | 典型写法 | 为什么会变 |
|---|---|---|
| 未提交清单 | 「以下四项尚未入库」 | 提交后立刻变成错的 |
| 提交笔数 | 「两次本地提交」 | 再提交一次就错了 |
| 提交序号 | 「第二次提交 `bb7c4c8`」 | 后续提交会让序号错位 |
| 执行次数 | 「一次实际执行记录」 | 次数随时间增长 |
| 状态快照 | 「工作区当前 0 条待处理」 | 下一次改动即失效 |

### 3.3 判据是稳定性，不是具体程度

- 规则二拦的不是「写得具体」，而是「这条信息会不会因为提交而变成假的」。颗粒度不是判据，稳定性才是。
- 常见的误读是把它当成「不许写具体参数」。按这个口径去执行，会同时犯两类错：既漏掉「已提交」这类不具体却必然失真的表述，又会误伤仍登记指纹的历史交接文档里写死的精确字节数与完整 SHA-256——那些恰恰是必须写具体的。
- 「已提交」三个字不含任何数字，照样属禁止项：再改一次文件，它立刻失真。
- 对照如下：

| 写法 | 具体吗 | 会随提交失真吗 | 规则二 |
|---|---|---|---|
| 「以下四项尚未入库」 | 具体 | 会 | 禁 |
| 「本篇已提交」 | 不具体 | 会 | 禁 |
| 「两次本地提交」 | 具体 | 会 | 禁 |
| `03ob_c1提交流程` 为 13046 字节 / 216 行 | 具体 | 不会 | 允许 |
| 「提交格式见 `03` 第 8.1 节」 | 不具体 | 不会 | 允许 |

- 判据可以压成一句：**提交这个动作本身，会不会改变这句话的真假？**会，就换写法；不会，随便写多具体。

### 3.4 替代表述

- 把「现在是什么状态」换成「到哪里查状态」：写以 `git log`、`git status` 为准，而不是把当下的值写死进文档。
- 要表达改动后的状态，就只写**已经发生的事**，不对「提交到哪一步」下断言。「本会话新增了 `note/10`，并登记到 `00总览` 第 2.6 节与库根 `README`」同样具体，但它不会被提交动作作废。
- 不为每次订正单列小节、不排号，避免「提交完成后才发现序号写错」这类问题。

## 4. 提交流程

- 本章自 [[03ob_c1提交流程-2026-10-05]] 第 8 章迁入，是该篇正文的现行版本；该篇已冻结，其第 8 章不再维护，执行细节以本章为准。
- 流程覆盖到 `git commit` 为止；推送是独立动作，一律需单独授权。

### 4.1 标准流程

1. 先按第 2 章把该同步的改动做完：文档状态表述、[[00handover总览]]、[[00note总览]] 与库根 `README.md` 里的对应条目，以及改动涉及的仍登记指纹的历史交接文档，全部纳入同一次提交。
2. 按第 3 章检查待提交文档里有没有会随提交动作变化的事实，有则改为指向 `git log`、`git status` 的表述。**不要只看正文**：元信息一类的头部字段同样要逐个键看过——交接文档的「接手方需要先知道」「交接状态」都在此列，它们位于冻结文档的可改位置内，最容易被当成历史叙述放过。
3. 取得待提交路径清单，含未跟踪目录内的文件。
4. 把本单元写下的断言句抄成清单（元信息字段、正文表尾、总览摘要行），逐句问「第 3 步的路径清单能不能满足这句话」：断言点名了文件或数量的，清单里必须出现对应文件，出现不了就是本笔已经失真。例如写下「活跃文档的引用已全部同步」，则清单里必须出现全部活跃文档。分不清的一律改为指向 `git log` 的表述（第 3.4 节）。这条取代不了人工判断，但把断言与文件清单强制并置，不再依赖记忆。
5. 逐文件比对工作区与 `HEAD` 的命中值，只对新增值拦截；有新增即中止，不暂存。
6. 打印报告：文件、规则、命中次数，不回显内容。
7. 全部通过后暂存，复核暂存统计，再提交。
8. 推送不在本流程内，需单独授权。

### 4.2 命令骨架

```powershell
$repo = 'D:\User\Documents\Obsidian\ob_c1'
$sd = @('-c', "safe.directory=$repo", '-c', 'core.quotepath=false', '-C', $repo)

# 1. 待提交路径（含未跟踪目录内的文件）
$por = @(git @sd status --porcelain=v1 --untracked-files=all)

# 2. 扫描：工作区命中值与 HEAD 命中值逐值比对，只有新值才中止
#    重命名过的文件要连旧路径一起取 HEAD 内容，否则会把改名当成新增暴露

# 3. 通过后暂存与提交
git @sd add -A
git @sd diff --cached --stat
git @sd commit -m '<提交信息>'
```

- 命令在 Windows PowerShell 中执行，执行目录为库根。

### 4.3 扫描规则

- 硬禁级：GitHub Token、GitHub PAT、`sk-` 前缀的长密钥、AWS Access Key、私钥块、`password`／`secret`／`api_key` 等键值型凭据、内网 IP、本机主机名。
- 应当级：真实用户名、邮箱地址。
- 报告只输出文件、规则与命中次数；**不得**回显命中内容。
- 已知误报：邮箱规则会命中 SSH 克隆地址里的固定用户名（形如 `git@` 加域名）。判定要按字面量确认，不能只看正则是否命中，也可把该常量直接列入白名单。
- 自撞风险：若文档里为了说明规则而写出规则名本身，宽松写法可能自撞；规则里的长度阈值（例如密钥至少 20 个字符）能避免这一类自撞。
- 「第三方中继域名」已于 2026-10-05 从应当级移除：中继域名属于会随订阅与服务商变化的不稳定项，写进扫描规则即成为需要持续维护的易变事实（违背 [[05Markdown规范]] 第 13 章的口径）；该风险改由 `%USERPROFILE%\.dsh\AGENTS.md` 的外发条款以行为约束覆盖。移除经过见 [[03ob_c1提交流程-2026-10-05]] 第 8.3 节。

## 5. 两条规则的关系

- 规则一管**动作顺序**：什么时候提交。
- 规则二管**写作内容**：文档里能写什么。
- 两者是同一件事的两面：规则一要求提交前消灭所有过时表述，规则二让文档里不产生会过时的表述。少了规则二，规则一就退化成「每提交一次都要回头改一遍文档」。
- 所以规则一落地时规则二必须同时生效；只做规则一，返工只是被推迟。

## 6. 实例与改法

| 原文写法 | 问题 | 改后 |
|---|---|---|
| 「四项尚未入库」 | 提交后立刻过时 | 只写已发生的提交，实时状态以 `git log`、`git status` 为准 |
| 「两次本地提交」 | 笔数会变 | 去掉笔数，改成不带次数的表述 |
| 「一次实际执行记录（`ab8b450`）」 | 次数加单次快照 | 改为不带次数的表述 |
| 「第二次提交 `bb7c4c8`」 | 序号会错位 | 不标提交序号，只写该次提交做了什么 |

- **判定阈值（2026-10-11 由用户定为）**：累计满 10 个工作单元后作一次判定。失败样本 ≤ 2 判「暂稳定」，≥ 3 判「不稳定，须补预防项」。10 这个量级能让 20% 的失败率以约 80% 的概率至少被观察到一次；阈值到点前不作结论（提前触发的例外与计数方式见下条）。
