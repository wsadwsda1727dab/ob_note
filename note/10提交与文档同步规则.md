# 提交与文档同步规则

> 文档名称：提交与文档同步规则
> 适用范围：本地提交前的同步检查，以及文档中与提交状态相关表述的写法约束
> 适用对象：本库作者，以及协助写作与提交的 AI
> 最近更新：2026-10-05
> 关联文档：[[05Command]]、[[00note总览]]、[[03ob_c1提交流程-2026-10-05]]、[[01交接文档写作格式]]

## 1. 适用范围与规则强度

### 1.1 适用范围

- 本篇记录两条相互配套的规则：一条管**什么时候提交**，一条管**文档里能写什么**。
- 规则的来源是一次返工：先提交、后发现关联文档过时，连续产生多笔补提交，每次都要重跑扫描、重算指纹，由此总结出这两条。
- 原始落点在 `handover/` 下的两份文档：[[03ob_c1提交流程-2026-10-05]] 第 8.1 节第 1、2 步与第 4.6 条决策，[[01交接文档写作格式]] 第 5 章与第 8 章自查表。本篇是它们的汇总说明。
- 效力范围：规则二已提升为全库规则，写在 [[05Command]] 第 13 章，约束 `note/` 与 `handover/` 下的全部文档；规则一仍只属于提交流程，宿主是 [[03ob_c1提交流程-2026-10-05]]。两项范围的由来见第 6 章。

### 1.2 规则强度

- 沿用 [[05Command]] 第 1.2 节的口径：**必须**是硬约束，**应当**是默认做法，**可以**是可选。
- 两条规则在其原始落点里都是硬约束：提交前**必须**先把该同步的改完，文档里**不得**写入会随提交动作变化的事实。

### 1.3 与既有规范的关系

| 文档 | 管什么 | 与本篇的关系 |
|---|---|---|
| [[05Command]] | 全库 Markdown 写作与输出格式 | 规则二的正式落点（第 13 章）；格式规则以它为准 |

## 2. 规则一：提交前先同步

### 2.1 规则内容

- 动手 `git commit` 之前，先把本次改动引发的所有关联变动做完，纳入同一次提交。
- 顺序是「改完 → 同步 → 提交」，不是「提交 → 发现过时 → 再补一笔」。
- 改完 `handover/` 文档要回头检查索引；索引更新后要回头检查引用它的文档。

### 2.2 需要同步什么

- **文档状态表述**：受影响文档里对当前状态的描述。
- **指纹**：字节数、行数与完整 SHA-256。
- **索引条目**：`[[00handover总览]]` 与库根 `README.md` 里的对应行。

- 判据只有一句：这次改动会不会让别的文件里的某句话变成错的？会，就在提交前改掉。

### 2.3 理由与代价

- **代价对比**：先同步多一道自查；先提交省一次停顿，但提交动作本身会让刚提交的文档失真，只能追加补提交，而每次补提交都要重跑扫描、重算指纹。
- **结论**：选先同步，一次提交即形成自洽状态。
- **被否决的选项**：先提交、发现问题再补。
- **反悔方式**：删掉 [[03ob_c1提交流程-2026-10-05]] 第 8.1 节第 1、2 步。
- **已知局限**：这条规则有效但不自动成立——改为该规则之后仍出现过返工。

## 3. 规则二：不写会随提交动作变化的事实

### 3.1 规则内容

- 文档里**不得**写入会随提交动作变化的事实，改为指向 `git log`、`git status` 的表述。
- 原因是自指问题：当文档描述的状态里包含「这份文档自己有没有被提交」这件事时，提交动作一发生，描述立刻失真。

### 3.2 哪类事实属于禁止项

| 类别 | 典型写法 | 为什么会变 |
|---|---|---|
| 未提交清单 | 「以下四项尚未入库」 | 提交后立刻变成错的 |
| 提交笔数 | 「两次本地提交」 | 再提交一次就错了 |
| 提交序号 | 「第二次提交 `bb7c4c8`」 | 后续提交会让序号错位 |
| 执行次数 | 「一次实际执行记录」 | 次数随时间增长 |
| 状态快照 | 「工作区当前 0 条待处理」 | 下一次改动即失效 |

### 3.3 判据是稳定性，不是具体程度

- 规则二拦的不是「写得具体」，而是「这条信息会不会因为提交而变成假的」。颗粒度不是判据，稳定性才是。
- 常见的误读是把它当成「不许写具体参数」。按这个口径去执行，会同时犯两类错：既漏掉「已提交」这类不具体却必然失真的表述，又会误伤 [[01交接文档写作格式]] 第 4.2 节要求写死的精确字节数与完整 SHA-256——那些恰恰是必须写具体的。
- 「已提交」三个字不含任何数字，照样属禁止项：再改一次文件，它立刻失真。
- 对照如下：

| 写法 | 具体吗 | 会随提交失真吗 | 规则二 |
|---|---|---|---|
| 「以下四项尚未入库」 | 具体 | 会 | 禁 |
| 「本篇已提交」 | 不具体 | 会 | 禁 |
| 「两次本地提交」 | 具体 | 会 | 禁 |
| `03ob_c1提交流程` 为 13046 字节 / 216 行 | 具体 | 不会 | 允许 |
| 「提交格式见 `03` 第 8.1 节」 | 不具体 | 不会 | 允许 |

- 判据可以压成一句：**提交这个动作本身，会不会改变这句话的真假？**会，就换写法；不会，随便写多具体。

### 3.4 替代表述

- 把「现在是什么状态」换成「到哪里查状态」：写以 `git log`、`git status` 为准，而不是把当下的值写死进文档。
- 要表达改动后的状态，就只写**已经发生的事**，不对「提交到哪一步」下断言。「本会话新增了 `note/10`，并登记到 `00总览` 第 2.6 节与库根 `README`」同样具体，但它不会被提交动作作废。
- 不为每次订正单列小节、不排号，避免「提交完成后才发现序号写错」这类问题。

## 4. 两条规则的关系

- 规则一管**动作顺序**：什么时候提交。
- 规则二管**写作内容**：文档里能写什么。
- 两者是同一件事的两面：规则一要求提交前消灭所有过时表述，规则二让文档里不产生会过时的表述。少了规则二，规则一就退化成「每提交一次都要回头改一遍文档」。
- 所以规则一落地时规则二必须同时生效；只做规则一，返工只是被推迟。

## 5. 实例与改法

| 原文写法 | 问题 | 改后 |
|---|---|---|
| 「四项尚未入库」 | 提交后立刻过时 | 只写已发生的提交，实时状态以 `git log`、`git status` 为准 |
| 「两次本地提交」 | 笔数会变 | 去掉笔数，改成不带次数的表述 |
| 「一次实际执行记录（`ab8b450`）」 | 次数加单次快照 | 改为不带次数的表述 |
| 「第二次提交 `bb7c4c8`」 | 序号会错位 | 不标提交序号，只写该次提交做了什么 |

- 这批改法实际发生在 `handover/` 文档的整理过程中，逐条记录见 [[04handover总览与库根README-2026-10-05]] 第 3.8、3.9 节。
