## 1. 适用范围与优先级

### 1.1 适用范围

- 本规范适用于 `note/` 下的全部 Markdown 文档。
- AI 在聊天框中输出 Markdown 时，同时受第 10 章约束。
- 目录结构与命名约定以 [[00note总览]] 为准，本规范不重复定义。

### 1.2 规则强度

- **必须**：硬约束，违反即视为不合格。
- **应当**：默认做法，有正当理由时可偏离，但要在交付说明中写清理由。
- **可以**：可选，按需使用。

### 1.3 冲突优先级

1. 用户当次的明确要求
2. 本规范
3. 其他文档的既有写法与工具默认习惯

- 无法满足本规范的某条要求时，**必须**在回复中说明是哪一条、为什么不满足，**不得**静默忽略。
- 本规范与库内其他文档的写法冲突时，以本规范为准；命名、路径、目录结构以 [[00note总览]] 为准。

## 2. 标题与编号

### 2.1 层级与含义

- H1（`#`）是文档标题，一篇只有一个，**不带编号**，用来点明整篇文档的主题。
- H2（`##`）是章节，也就是一级标题，编号形如 `1.`、`2.`。
- H3（`###`）是小节，编号形如 `1.1`、`2.3`。
- H4（`####`）是更细的分组，编号形如 `1.1.1`、`2.3.4`。
- 最多用到 H4；更深的内容改用列表或表格，不再增加标题层级。

### 2.2 编号写法

- 编号与标题文字之间保留一个半角空格：`## 1. 适用范围`、`### 1.1 适用范围`。
- 父级编号在下级中重复出现：第 1 章的小节是 `1.1`、`1.2`，第 2 章的小节是 `2.1`、`2.2`。
- 同一层级编号从 1 开始、连续递增，不重复、不跳号；每篇文档各自从 1 开始。
- 编号末尾只保留一个点，不要写成 `1..` 或 `1.2.`。

### 2.3 不跳级

- 不能从 H1 直接跳到 H3，中间必须有对应层级。
- 正确：`# 标题` → `## 1. 章节` → `### 1.1 小节`。
- 错误：`# 标题` → `### 1.1 小节`。

### 2.4 标题文字

- 同一篇文档内的标题文字**必须**唯一，便于用 `[[#标题]]` 跳转。
- 标题中不要出现换行、`#`、`[`、`]`。
- 标题**应当**避免 emoji 与装饰符号（如 `⚠️`），否则 `[[#标题]]` 锚点难以输入。
- 标题末尾不加句号。

## 3. 分隔线

- 分隔线写作独立一行的 `---`。
- **只在一章结束时加一条**，即每个 H2 章节的最后一条内容之后，用来隔开下一章。
- 分隔线前后**必须**各空一行：
  - 前面空行：避免紧跟在正文段落后的 `---` 被部分渲染器解析成 setext 二级标题。
  - 后面空行：便于阅读下一章标题。
- 文档标题与元信息区之后**不加**分隔线，因为那不是章节末尾。
- 章内（H3、H4 之间）**不加**分隔线，不要用分隔线替代标题层级。
- 最后一章同样加，文档以 `---` 加换行结束。

---

## 4. 段落、空行与列表

### 4.1 空行

- 标题前后各空一行。
- 代码块、表格、列表、引用块的前后各空一行。
- 段落之间空一行；段落内部**不要**靠单个换行来分行，Obsidian 未开启严格换行时单换行不生效。
- 确需在段落内强制换行时，在行尾加两个空格；能拆成段落或用列表表达的，优先拆分。

### 4.2 列表

- 无序列表统一用 `-`，不要混用 `*`、`+`。
- 有序列表统一用 `1.`、`2.`、`3.`，按实际顺序写数字。
- 任务清单用 `- [ ]`（未完成）与 `- [x]`（已完成）。
- 缩进统一用 2 个空格，**不要**用 Tab；嵌套不超过 3 层。
- 列表项内的代码块要与该列表项正文左对齐（通常缩进 2 个空格）；顶格缩进 4 个空格会被解析成缩进代码块。

## 5. 排版与文字

### 5.1 中英文与标点

- 中文与英文、数字之间加一个半角空格：`使用 Git 安装`、`Node.js 18+`。
- 例外：行内代码与代码块内部、URL、文件名、路径不加空格；全角标点两侧不加空格。
- 中文内容用全角标点（，。：；！？），英文与代码用半角标点（, . : ; ! ?）。
- 中文引号用 `“ ”`、`‘ ’`，注意成对且方向正确，不要写成 `” ”`。
- 中文语境用全角括号 `（）`；括号内是纯英文或代码时可用半角 `()`。

### 5.2 术语、日期与版本

- 术语大小写按第 11 章术语表，同一篇文档内不得出现两种写法。
- 日期统一 `YYYY-MM-DD`；需要精确到时刻时用 `YYYY-MM-DD HH:MM`（本机时区）。
- 版本号用语义化版本，如 `1.7.0`。
- 仅安装、配置、操作类文档需要标版本与变更记录；纯知识说明类文档不必强行加版本。

### 5.3 行内代码与强调

- 命令、文件名、路径、变量、参数、键名用行内代码：`` `SKILL.md` ``、`` `npx skills` ``。
- 行内代码本身含反引号时，用双反引号包裹：`` ``a`b`` ``。
- 强调用 `**加粗**`；不要用行内代码代替强调，也不要整段加粗。
- **应当**优先使用 Markdown 原生语法；确有必要时才用 `<br>` 等 HTML 标签。

### 5.4 表格

- 表头行与分隔行**必须**完整，例如：

```markdown
| 参数 | 说明 |
|---|---|
| `-r` | 递归处理文件夹 |
```

- 分隔行用 `|---|` 表示左对齐（默认）；需要右对齐时用 `|---:|`；不要用居中。
- 单元格内不换行、不写长段落；内容过长时改用列表或拆分表格。
- 单元格内出现 `|` 时写作 `\|`，行内代码里的 `|` 同样要转义。
- 表格前后各空一行。

## 6. 代码块与命令

### 6.1 语言标注

- 代码块**必须**标注语言：起止围栏均用三个反引号，起始围栏后直接写语言名。
- 常用语言名：`bash`、`powershell`、`cmd`、`json`、`yaml`、`toml`、`ini`、`python`、`sql`、`diff`、`js`、`gitignore`、`gitattributes`、`text`、`markdown`。
- 命令输出、日志、纯文本用 `text`；确实没有合适语言名时也用 `text`，**不要**留空。
- 语言名一律小写。

### 6.2 命令与执行环境

- 涉及命令时**必须**写清执行环境：Windows `cmd`、Windows PowerShell、macOS 或 Linux `bash`。
- 跨平台写法差异较大时分别列出，避免直接复制后报错。
- **应当**标注执行目录，例如“在仓库根目录执行”。
- 破坏性命令（删除、重置、覆盖、`git reset --hard`、`rm -rf` 等）**必须**同时给出备份或回滚方式与风险提示。
- 安装、配置类文档**应当**给出可直接复制执行的命令，并注明前置条件（管理员权限、需要先退出某个程序等）。

## 7. 链接与图片

- 库内文档互链用双链：`[[01GitCommand]]`；需要显示别名时用 `[[05Markdown规范|写作规范]]`。
- 指向库内某一标题用 `[[05Markdown规范#2. 标题与编号]]`。
- 库内图片与附件用嵌入双链：`![[图片.png]]`。
- 外部链接用 `[文本](URL)`，保留原始 URL，不使用短链或跳转服务。
- 不要只贴裸 URL，应当给出可读文本或来源说明。
- 文档改名或标题调整后，**必须**同步更新引用它的双链，避免死链。

## 8. 文件与交付

### 8.1 写文件

- 用户要求“写进文件”时**必须**优先使用文件写入工具，而不是把全文贴在聊天里。
- 修改已有文件前先读原文件；能用局部替换就不要整篇覆盖。
- 不能直接写本地文件时，输出纯文本源码，并说明需要用户手动保存为 `.md`。
- 写入后**应当**在回复中给出文件路径与本次改动摘要。

### 8.2 文件名与位置

- 长期知识正文放在 `note/`；`handover/` 的交接文档与 `templates/` 的模板按其自身规范存放。库根只保留仓库配置与库级说明，即 `.obsidian/`、`.gitattributes`、`.gitignore`、`README.md`、`AGENTS.md`，以及项目级 Skills 目录 `.agents/` 与它的清单 `skills-lock.json`。
- `note/` 下的文件名遵守 [[00note总览]] 的命名约定：`NN名称.md`，`NN` 为两位序号；英文名称不用下划线、每个单词首字母大写，中文名称直接连写。其他目录的命名按各自规范：`handover/` 见 [[01交接文档写作格式]]，`templates/` 见 [[00模板说明]]。
- 命名例外：总览文件命名为 `00note总览.md`，其中 `note` 保持小写，不受上一条「每个单词首字母大写」的约束。
- 新增笔记顺延编号；已存在的文件名默认沿用不改。确需统一命名规则时可以批量改名，但改名后**必须**按第 7 章同步更新全部双链与 [[00note总览]] 里的引用，避免死链。
- 文件名中不得出现 `\ / : * ? " < > |`，也不得有首尾空格。

### 8.3 编码与行尾

- 所有 Markdown 文件保存为 UTF-8，且不带 BOM。
- 行尾统一 LF，与 `.gitattributes` 中的 `* text=auto eol=lf`、`*.md text eol=lf` 保持一致；不要在 Windows 上用 CRLF 写入。
- 文件末尾保留一个换行。

### 8.4 文档元信息

- 元信息可选，形式固定为标题下方的引用块，每行一条 `> 键：值`，例如：

```markdown
> 文档名称：DSH 插件安装方法与步骤
> 适用范围：图形界面安装、命令行安装、兼容性排查与回滚
> 最近更新：2026-10-02
```

- 常用键：文档名称、适用范围、适用对象、最近更新、关联文档。
- 本库不使用 YAML frontmatter，因为它的 `---` 定界符与第 3 章的分隔线语义冲突。

### 8.5 目录

- 章节数达到 8 章，或正文超过 300 行时，**应当**在元信息之后加目录。
- 目录标签写一行 `**目录**`，不使用标题语法，避免占用章节编号。
- 目录条目用双链指向章节标题：`- [[#1. 适用范围与优先级]]`。

### 8.6 附件

- 图片、PDF、压缩包等附件统一放在 `note/attachments/`，用 `![[文件名]]` 引用，不要放在库根。

### 8.7 变更记录

- 操作类文档**应当**在文末加一章“变更记录”，用表格记录日期与改动：

```markdown
| 日期 | 版本 | 变更 |
|---|---|---|
| 2026-10-02 | 1.0.0 | 初版 |
```

## 9. 敏感信息

- 文档中**不得**出现真实 token、密码、私钥、密钥、cookie、内网 IP、内网主机名。
- 真实用户名**应当**用 `%USERPROFILE%` 或 `<用户名>` 等占位符代替；确需记录本机绝对路径时，只写盘符与目录层级，不写用户名。
- 示例中的域名、账号、路径一律用占位符，例如 `example.com`、`<你的路径>`。
- 分享日志、截图、命令输出前先脱敏，确认无上述内容。

## 10. AI 聊天输出约定

- 用户明确说“输出 md 文档”或“写进 md 文档”时：输出纯文本 Markdown 源码，用四个反引号包裹并标注 `markdown`，前后不加多余解释文字。
- 用四个反引号包裹，是为了让文档内部的三个反引号代码块保持完整。
- 用户说“写进文件”时按第 8.1 节处理：直接写文件，聊天里只给路径与改动摘要，不重复贴全文。
- 用户没有明确要求输出 md 源码时（普通提问、解释、命令结果分析），按正常聊天方式回复，不输出待保存的源码。
- 用户说“正常回复”时，一律不使用四反引号包裹。

## 13. 提交状态表述

- 文档中**不得**写入会随提交动作变化的事实，这类信息一律改成指向 `git log`、`git status` 的表述。
- 原因是自指问题：当文档描述的状态里包含「这份文档自己有没有被提交」时，提交动作一发生，描述立刻失真。

### 13.1 禁止写入的内容

- 未提交清单，例如「以下四项尚未入库」。
- 提交笔数，例如「两次本地提交」。
- 提交序号，例如「第二次提交 `bb7c4c8`」。
- 执行次数，例如「一次实际执行记录」。
- 状态快照，例如「工作区当前 0 条待处理」。

### 13.2 允许写入的内容

- 判据是**稳定性**，不是具体程度：要看提交动作本身会不会改变这句话的真假。
- 已经发生的事实可以写，写多具体都行，例如「本会话新增了 `note/10`，并登记到 [[00note总览]] 第 2.6 节」。
- 哈希、字节数、行数这类指纹只要不再改动对应文件就仍然有效，写了就写全，不要因为「怕过时」而省略；自 2026-10-10 起新建的交接文档不再登记指纹，见 [[01交接文档写作格式]] 第 2.3、3 章。

### 13.3 替代表述

- 把「现在是什么状态」换成「到哪里查状态」，以 `git log`、`git status` 为准。
- 不排号：不为每次订正单列小节，避免「提交完成后才发现序号写错」。

## 14. 已闭环事项的标注

- 适用范围是 `handover/` 下的未决事项表，包括两处：总览文档 [[00handover总览]] 第 5 章的汇总表，以及各来源文档（`02`、`03`、`04` 等）「未决事项与下一步」章「等用户决定」小节的表格（2026-10-08 之前的旧模板为第 7.1 节，之后为第 3.1 节）。
- 两处的处理方式不同：来源文档的未决事项表加删除线并保留原行；总览第 5 章的汇总表删除该行。
- 来源文档的未决事项表：某项闭环后，给该行「事项」文字加删除线，写作 `~~文字~~`。
- 来源文档的未决事项表：只改「事项」一列，前置条件、优先级、决定方三列保持原样。
- 来源文档的未决事项表：已闭环**只**用删除线表示，不再另写 `**已完成**` 之类的前缀，也不要前缀与删除线并用。
- 来源文档的未决事项表：行**必须**保留，不整行删除；删除线表示已闭环，行留着是为了回头核对当初的备选项与被否决的理由。
- 总览第 5 章：某项闭环后，直接从汇总表删除该行，不在表内保留划线行；汇总表只列尚未闭环的项。
- 闭环的日期与结论写在紧邻表格的说明列表里，或写在来源文档「决策与理由」章的对应条目里；同一事实只在一处写全，另一处指向它即可。
- 两处**必须**在同一批改动里一起改，不得只改一处：一处加删除线、一处删行。
- 本规则只适用于 `handover/` 下的这两处表格，不扩到 `note/` 下的未决事项表。

### 14.1 写法示例

```markdown
| 事项 | 前置条件 | 优先级 | 决定方 |
|---|---|---|---|
| ~~是否清理 3 个备份~~ | 确认新条款稳定使用一段时间 | 低 | 用户 |
| 是否为 3A 方案查证 DSH 能力 | 允许解包安装目录归档 | 低 | 用户 |
```

- 上表是来源文档的未决事项表的写法：第一行是已闭环项，第二行是未闭环项，两行都保留，未闭环项不加任何标记。
- 总览第 5 章不照此写法：上表第一行那样的已闭环项直接从汇总表删除，表内只留未闭环项，示例见 [[00handover总览]] 第 5 章。
