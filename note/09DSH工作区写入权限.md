## 1. 问题现象

在 DSH 会话工作区 `D:\User\Documents\Obsidian\ob_c1` 中观察到一组自相矛盾的现象：

- shell（`pwsh`）无法向已存在的子目录 `note/`、`.obsidian/` 写入文件，报 `UnauthorizedAccessException：访问被拒绝`。
- 同一个 shell 却能向工作区**根目录**写入新文件，也能删除自己刚创建的文件。
- 在根目录新建子目录后，向其中写入**正常**。
- 换成 DSH 的文件写入工具（write / edit）修改 `note/` 下的文件，**完全正常**。

也就是说，被挡住的是已有子目录，而且只影响 shell 通道，不影响文件工具通道。

本库已于 2026-10-02 按第 5.2 节完成修复（全库 304 个对象补上 Low 标签），上述受限现象已消除；本章及以下内容保留，作为同类问题的排查参考。

## 2. 根本原因

### 2.1 强制完整性标签

Windows 有一套独立于账户权限的强制完整性控制（Mandatory Integrity Control）：

- 每个进程和每个可保护对象（文件、目录）各自带一个完整性级别（IL）。
- DSH 的 Windows 沙箱把 shell 进程降为低完整性（Low，`S-1-16-4096`）。
- 对象的标签默认策略禁止向上写（`NW`，No-Write-Up）：低完整性进程写不进完整性更高的对象。
- 对象完全没有标签时按中等完整性（Medium）对待，低完整性进程同样写不进去。

关键在于这一层判定与 DACL（哪个账户有什么权限）互相独立，DACL 允许也会被它拦下。

### 2.2 标签的实际分布

| 对象 | 完整性标签 | 低完整性 shell 能否写入 |
|---|---|---|
| 工作区根目录 `ob_c1` | `Mandatory Label\Low Mandatory Level:(OI)(CI)(NW)` | 能 |
| `note/`、`.obsidian/` 及库内既有文件 | 无标签（按 Medium 处理） | 不能 |
| 根目录下新建的目录与文件 | 继承 `(I)(OI)(CI)(NW)` 的 Low 标签 | 能 |

### 2.3 子目录为什么没有标签

- 标签继承只在创建对象时发生：新对象把父目录的可继承标签复制一份，标记为继承 `(I)`。
- 对已经存在的对象不会回填，除非显式递归。
- 工作区根目录的标签来自 DSH 的沙箱 provision，而它只作用于根目录这一个对象（同批写入的沙箱授权 `S-1-4-*` 同样只出现在根目录上）。`note/`、`.obsidian/` 都在这之前就已存在，此后也没人递归补齐，所以至今一条标签都没有。
- 因此，缺标签与目录是否被导入 DSH 无关，本质是打标签时子目录已经存在，而标签继承不追溯。换成任何方式给一个已有内容的目录打标签，结果都一样。

## 3. 诊断方法

### 3.1 确认进程完整性级别

Windows PowerShell（`pwsh` 或 `powershell`，任意目录）：

```powershell
whoami /groups | Select-String 'Mandatory Label'
```

输出 `Mandatory Label\Low Mandatory Level  S-1-16-4096`，就说明当前 shell 是低完整性。

### 3.2 确认标签分布

```powershell
$root = 'D:\User\Documents\Obsidian\ob_c1'
icacls $root | Select-String 'Mandatory Label'
icacls (Join-Path $root 'note') | Select-String 'Mandatory Label'
```

根目录有输出、子目录无输出，就是本文描述的情形。

### 3.3 排除 ACL 因素

```powershell
Get-Acl 'D:\User\Documents\Obsidian\ob_c1\note' |
  Select-Object -ExpandProperty Access |
  Select-Object IdentityReference, FileSystemRights, AccessControlType
```

若当前账户在目标目录上已有完全控制或修改，却仍被拒绝，即可判定问题在完整性标签而不是 DACL，补权限（`icacls /grant`）不会有任何效果。

### 3.4 判据小结

- 根目录可写、既有子目录被拒，就是标签缺失。
- 根目录可写同时说明 DSH 的沙箱策略本身允许在工作区内写入，不是路径策略问题。

### 3.5 与 DSH 内置 ACL 诊断技能的关系

DSH 内置了一个用于排查 Windows 沙箱访问被拒的技能 `diagnose-windows-sandbox-acl`，它属于 DSH 的技能体系，来源与安装层级见 [[04Skills]]。弄清它与本文的分工，可以避免在错误的方向上反复修补。

- **它能做什么**：检查目标路径及其每一级父目录上的有效 `WRITE_DAC` 与 `WRITE_OWNER`，在同一次运行内修复它已经证明的问题，并移除 `S-1-15-2-*` 这类 AppContainer 包授权条目。它还会把 `S-1-4-*` 授权与 `Everyone` 的删除拒绝判为预期项，而这两条恰好容易被误认成元凶。
- **它不能做什么**：脚本只读取并记录标签状态（输出里的 `LOW_LABEL`），从不写标签。
- **对本例的意义**：所以按技能跑完 ACL 修复，低完整性 shell 仍然写不进 `note/`，因为缺的是标签而不是权限条目。补标签需要 `SeSecurityPrivilege`，沙箱令牌里没有，只能走第 5.2 节的提权路径。
- **分工结论**：技能负责 ACL 一侧，本文第 5.2 节负责完整性标签一侧，两者互补，缺一不可。

## 4. 影响范围

| 场景                                           | 是否受限                                   |
| -------------------------------------------- | -------------------------------------- |
| write / edit 工具读写 `note/` 下的文件               | 不受限                                    |
| shell 写工作区根目录，以及根目录下新建的目录                    | 不受限                                    |
| shell 写既有子目录（`note/`、`.obsidian/`、`.git/` 等） | 受限，被拒绝                                 |
| shell 中运行 `git` 提交、脚本往既有子目录生成文件              | 受限（`git` 报无法创建 `index.lock` 之类多半是同一原因） |
| Obsidian 等中等完整性程序读写库文件                       | 不受限                                    |

结论：日常用 DSH 文件工具改笔记不受影响，受影响的只是 shell 里的写入这一类操作。

## 5. shell 写入修复方案

### 5.1 临时做法

改既有目录中的文件时走 DSH 的文件写入工具（write / edit），不要用 shell 重定向或脚本写入。

### 5.2 根治：一次性递归补标签

Windows PowerShell，以管理员身份运行，执行目录任意：

```powershell
icacls 'D:\User\Documents\Obsidian\ob_c1' /setintegritylevel (OI)(CI)low /T
```

- 作用：给根目录及全部既有子项补上低完整性标签，此后新建的对象自动继承。
- `(OI)(CI)` 让标签可向下继承，`/T` 才会处理已有子项；不加 `/T` 只作用于该目录本身，这正是当前状态的来源。
- 风险：低。只放开低完整性进程向上写的限制，不改变任何账户的 DACL 权限，文件内容与所有者都不变。
- 回滚：把需要恢复的子目录改回 medium，等价于原来的无标签状态。

```powershell
icacls 'D:\User\Documents\Obsidian\ob_c1\note' /setintegritylevel (OI)(CI)medium
```

回滚时不要把工作区根目录改成 medium，否则沙箱连根目录也写不进去。

### 5.3 免管理员的替代做法

若目录内容可以搬迁：先把空目录设为工作区，再把旧内容复制进去。副本是在打标签之后创建的，会自动继承 Low 标签，全程不需要管理员操作。

## 6. 新建工作区的处理流程

1. 优先新建一个空目录，先设为 DSH 工作区，再把资料复制进去，无需任何手动补标签步骤。
2. 若目录中已有旧内容，设成工作区后按 3.2 节验证，发现子目录无标签就按 5.2 节补一次。
3. 验证方法：`icacls <路径> | Select-String 'Mandatory Label'`，出现 `Low Mandatory Level` 即正常。

| 目录状态 | 设为工作区后要做的事 |
|---|---|
| 空目录，之后拷入内容 | 什么都不用做 |
| 已经含有旧内容 | 管理员递归补一次标签，或把内容搬进新工作区 |

## 7. 常见疑问

### 7.1 这是不是目录先建好、后导入 DSH 造成的

现象上与时间顺序有关，但准确说法是打标签时子目录已经存在，而标签继承不追溯。导入本身不是原因，任何先有内容、后打标签的路径都会得到同样结果。

### 7.2 以后在 `note/` 里新建文件夹，能写吗

不能。`note/` 自身没有标签，它下面新建的目录也继承不到标签，会一直是 Medium，直到按 5.2 节递归补齐。

### 7.3 为什么补了 ACL 也没用

DACL 决定哪个账户有什么权限，完整性标签决定低完整性进程能否向上写，两者互不影响。当前账户在 `note/` 上已有完全控制，缺的是标签。

### 7.4 这是不是权限错乱或数据损坏

不是。目录没有标签是 Windows 的正常默认状态，只是沙箱 provision 没有对既有子项做递归。

### 7.5 会不会影响 Obsidian 与 Git 客户端

不会。标签只参与完整性级别判定，DACL 未变，中等完整性的程序照常读写；按 5.2 节补标签后，反而让 shell 里的 `git` 也能正常工作。
